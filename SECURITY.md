# Security Policy

## Scope

This project is a static website (no backend, no user accounts, no database) hosted on GitHub Pages. The main risks are in the supply chain (npm dependencies, GitHub Actions) and in repository access, not in server-side vulnerabilities.

## Supported versions

Only the latest version on the `main` branch (the one published on GitHub Pages) is supported.

## Reporting a vulnerability

Please **do not open a public issue** for security problems.

1. Go to the repository's **Security** tab and click **Report a vulnerability** (GitHub private vulnerability reporting).
2. Describe the problem, how to reproduce it and its potential impact.

You can expect an acknowledgement within a few days. Once a fix is published, the report may be disclosed and you will be credited if you wish.

## Best practices for this repository

### Secrets and data

- Never commit secrets (tokens, API keys, `.env` files, SSH keys). The project does not need any.
- If a secret is committed by mistake, revoke it immediately; removing it from git history is not enough.
- Only public game data and images are stored in the repo. Do not add personal data.

### Dependencies

- Keep `package-lock.json` committed and use `npm ci` in automated builds.
- Run `npm audit` before releasing and review updates before merging them.
- Add new dependencies only when really needed; the project intentionally keeps few.
- Prefer exact, well-known packages and double-check names to avoid typosquatting.

### GitHub Actions

- Keep workflow permissions minimal (the deploy workflow only needs `contents: read`, `pages: write`, `id-token: write`).
- Use trusted actions only (official `actions/*`) and keep them updated.
- Never print secrets in logs and never run untrusted code from pull requests with elevated permissions.

### Repository settings (recommended)

These are configured on GitHub, not in files:

- Enable **two-factor authentication** for every account with write access.
- Protect `main`: require pull requests and, if there are several maintainers, at least one approving review. Do not allow force pushes.
- Enable **Dependabot alerts** and **Dependabot security updates**.
- Enable **secret scanning** and **push protection**.
- Enable **private vulnerability reporting** (needed for the reporting process above).
- Give collaborators the lowest permission level they need.

### Contributions

- Review every pull request, especially changes to `.github/workflows/`, `package.json`, `package-lock.json` and `scripts/`.
- Be careful with data regenerated by `npm run data`: check the diff before merging, since it fetches content from an external site.
- Do not add external scripts, trackers or embeds to the site without discussion.
- Do not hotlink assets from other sites; store them in `public/` instead.
